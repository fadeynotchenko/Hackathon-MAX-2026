# Документы для бизнеса в MAX

Бот и мини-приложение мессенджера MAX, которые готовят типовые документы малого бизнеса: счёт на
оплату, коммерческое предложение, договор оказания услуг и акт. Владелец выбирает шаблон, отдаёт
данные формой, сообщением, голосом или фото, проверяет лист и получает готовый PDF или DOCX прямо
в чат, без компьютера и ручной замены реквизитов

Хакатон MAX 2026, трек «Эффективный бизнес», команда 409

## Сценарий пользователя

Мини-апп открывается кнопкой «Создать документ» в чате с ботом. Вкладки: «Создать», «Документы»,
«Профиль»

1. **Реквизиты один раз.** В профиле человек заводит свою организацию и карточки клиентов. ИНН,
   КПП, ОГРН, БИК и расчётный счёт проверяются контрольными суммами сразу при уходе с поля, а
   подсказки DaData заполняют карточку по названию или ИНН
2. **Шаблон.** Во вкладке «Создать» 16 стандартных бланков DOCX по образцам делового оборота и
   свои шаблоны. «Заполнить» сразу открывает форму, где реквизиты своей организации уже стоят, а
   номер документа подставлен следующим по счёту
3. **Данные.** Остальное вводится руками или помощником: текстом, голосовым, фото или сканом.
   Распознанное ждёт подтверждения кнопкой «Всё верно», у каждого значения виден источник
4. **Проверка.** «Проверить документ» показывает лист ровно таким, каким будет PDF: сумма прописью
   посчитана, незаполненное осталось линиями, ошибки стоят рядом с полем
5. **Отправка.** PDF или DOCX, затем «Отправить в чат»: бот присылает файл с сопроводительным
   текстом. Документ остаётся во вкладке «Документы» с историей отправки и доставки
6. **Дальше.** «Сделать акт» закрывает счёт или договор актом с теми же сторонами и суммой, «На
   основе этого» делает следующий такой же документ со свежими реквизитами

Стандартные шаблоны:

| Вид                      | Варианты                                                                     |
| ------------------------ | ---------------------------------------------------------------------------- |
| Счёт на оплату           | обычный, на товар, с НДС и основанием                                        |
| Коммерческое предложение | на бланке, краткое, с позициями                                              |
| Договор оказания услуг   | основной, между юрлицами, между физлицами, с ИП, с самозанятым, типовой      |
| Акт                      | выполненных работ, об оказании услуг, сдачи-приёма услуг ИП, приёма-передачи |

Свой шаблон делается из готового DOCX или PDF: места для данных находят метки `{{…}}`, помощник
или правила по линейкам и реквизитам, человек их проверяет. Чужой документ (договор от партнёра,
прошлый счёт) загружается через «Создать», «Изменить свой файл»: человек правит найденные значения
в той же форме, а файл собирается в копии загруженного, с его оформлением

Всё то же доступно в чате с ботом без мини-аппа. Сообщение «Счёт на 120 000 для ООО Ромашка за
разработку сайта» создаёт документ, бот показывает заполненные значения с кнопкой «Всё верно» и
после подтверждения присылает файл. Поправки («поменяй сумму на 150 000»), вопросы («чего не
хватает?»), голосовые и фото карточки предприятия работают так же, последнюю правку отменяет
кнопка «Отменить»

## Запуск одной командой

Нужен Docker с compose. Секреты лежат в `.env`, его нет в репозитории

```bash
cp .env.example .env
docker compose up --build
```

В `.env.example` у всех переменных, кроме `MAX_BOT_TOKEN`, уже стоят значения для локального
запуска. Значения `dev-only-…` в production отвергает валидатор конфигурации. Без настоящего
`MAX_BOT_TOKEN` поднимаются API и мини-апп, а бот не стартует (MAX отвечает 401). Пустой
`GIGACHAT_AUTH_KEY` выключает помощника, остальной сценарий работает

Стек из `compose.yaml` поднимает пять контейнеров: `db`, `redis`, `api`, `bot`, `web`, и
одноразовый `deps`, который ставит Node-зависимости. Сборка без кеша, не считая загрузки базовых
образов, укладывается в минуту на образ: ядро около 40 секунд, бот и gateway около 50

| Адрес                               | Что                                                |
| ----------------------------------- | -------------------------------------------------- |
| http://localhost:3090               | мини-апп (vite с HMR, `/api/` проксируется в ядро) |
| http://localhost:3090/api/v1/docs   | Swagger API                                        |
| http://localhost:3090/api/v1/health | состояние БД, Redis и потребителя событий бота     |

Вне production мини-апп в обычном браузере входит сам тестовым пользователем
(`DEV_LOGIN_ENABLED`). Бот локально работает через long polling и публичного адреса не требует.
Если тот же бот уже работает на проде через вебхук, локальный polling не запускается, чтобы не
снять подписку прода (`bot.polling.blocked` в логе), подробности в [docs/DEPLOY.md](docs/DEPLOY.md)

## Состав и архитектура

Один репозиторий, четыре сервиса. Каждая папка в корне является отдельной единицей деплоя со своим
рантаймом, образом и healthcheck

```
core/       Python 3.14, FastAPI: API мини-аппа, миграции, потребитель событий бота, владелец PostgreSQL
bot/        Node 24, @maxhub/max-bot-api: приветствие, диалог с помощником, доставка файлов в чат
web/        React 19, Vite, MAX UI: мини-апп «Создать, Документы, Профиль», вход по подписи initData
gateway/    nginx (прод): TLS, /api/ в ядро, вебхук бота, статика мини-аппа, лимиты, CSP
contracts/  OpenAPI ядра и JSON Schema событий, единственное общее между сервисами
docs/       продукт, пользовательские пути, архитектура, безопасность, деплой, логи, платформа MAX
```

```
MAX-клиент ─initData─▶ web ─/api/v1─▶ gateway ─▶ core ─▶ PostgreSQL
                                                  │  ├─▶ GigaChat, DaData
MAX ─вебхук─▶ bot ◀──── Redis Streams ────────────┘  └─▶ диск: DOCX и PDF
```

Сервисы не импортируют друг друга, это проверяют import-linter и dependency-cruiser. Шов ядра и
бота идёт через Redis Streams с типизированным контрактом: ядро публикует `document.ready`, бот
забирает файл по одноразовому токену и отправляет вложением, а затем отвечает отчётом о доставке.
Слои ядра, протокол событий, обработка ошибок и тесты описаны в
[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)

## Переменные окружения

Все переменные описаны в одном реестре `core.config.env_spec`. Корневой `.env.example`
генерируется из него и содержит описание, тип и значение по умолчанию каждой, а тест падает, если
файл отстал от реестра

| Переменная          | Обязательна | Зачем                                                         |
| ------------------- | ----------- | ------------------------------------------------------------- |
| `MAX_BOT_TOKEN`     | да          | токен бота из MasterBot, им же проверяется подпись initData   |
| `JWT_SECRET`        | да          | подпись access-токенов, 32 и больше случайных символов        |
| `DB_PASSWORD`       | да          | пароль PostgreSQL                                             |
| `REDIS_PASSWORD`    | да          | пароль Redis                                                  |
| `ADMIN_MAX_IDS`     | нет         | JSON-массив MAX-id администраторов, им открыт экран «Метрики» |
| `GIGACHAT_AUTH_KEY` | нет         | ключ GigaChat API: помощник, распознавание фото и голосовых   |
| `DADATA_API_KEY`    | нет         | подсказки организаций, банков и адресов в полях реквизитов    |
| `MAX_MINI_APP_NAME` | нет         | имя мини-аппа для кнопки `open_app` под сообщениями бота      |
| `WITH_PDF`          | нет         | `true` собирает образ ядра с LibreOffice и включает PDF       |
| `MEDIA_MAX_BYTES`   | нет         | предел файла на распознавание, по умолчанию 10 МБ             |
| `DEV_LOGIN_ENABLED` | нет         | вход тестовым пользователем вне production                    |
| `PUBLIC_BASE_URL`   | прод        | внешний адрес стенда для вебхука бота                         |

Полный список для прода с `DOMAIN`, `BOT_WEBHOOK_SECRET` и остальными находится в
[docs/DEPLOY.md](docs/DEPLOY.md)

## Зависимости

Версии зафиксированы lock-файлами: `core/uv.lock` (Python, менеджер `uv`) и `pnpm-lock.yaml`
(Node-воркспейсы `bot` и `web`). Образы собираются только по ним (`uv sync --frozen`,
`pnpm install --frozen-lockfile`)

| Где       | Основное                                                                               |
| --------- | -------------------------------------------------------------------------------------- |
| `core`    | FastAPI, SQLAlchemy 2 async, Alembic, redis.asyncio, PyJWT, python-docx, pypdf, Pillow |
| `bot`     | TypeScript 5.9, `@maxhub/max-bot-api`, ioredis, pino, zod                              |
| `web`     | React 19, Vite 8, `@maxhub/max-ui`, React Router                                       |
| Платформа | PostgreSQL 17, Redis 7, nginx 1.27, LibreOffice для PDF                                |

PDF собирается LibreOffice в образе ядра с `WITH_PDF=true`, вместе со шрифтами Liberation, Carlito
и Caladea. Это метрические аналоги Times New Roman, Arial, Courier New, Calibri и Cambria, которыми
свёрстаны бланки, поэтому строки в PDF переносятся так же, как в DOCX. Известные уязвимости
зависимостей проверяет `./maxapp audit`, на текущих lock-файлах он чист

  хранилище на один запрос и сразу удаляются
- Других интеграций нет. 1С и Госуслуги описаны в планах, но не подключены и нигде не имитируются.
  Смоделированы только вымышленные реквизиты для проверки, см. [тестовые данные](#тестовые-данные)

## Работа с данными

| Хранилище  | Что лежит                                                                                                      |
| ---------- | -------------------------------------------------------------------------------------------------------------- |
| PostgreSQL | пользователи, refresh-токены, шаблоны, организации с подписью и печатью, контрагенты, документы, журнал фактов |
| Redis      | сессии бота, потоки событий ядра и бота, одноразовые токены на скачивание файла (час)                          |
| Диск       | готовые DOCX и PDF в томе `app_data/api`, в базе их путь, размер и хеш                                         |

- Владелец PostgreSQL только `core`. Схемой владеют миграции Alembic, их применяет API при старте
  под advisory-lock
- Значение каждого поля хранится вместе с источником: ручной ввод, профиль, карточка клиента,
  помощник, распознанное фото. У распознанного хранится строка, из которой оно прочитано, и
  уверенность, само фото нигде не сохраняется
- Журнал фактов (создан, готов, собран, отправлен, доставлен, отклонён) пополняется только
  дописыванием и не содержит значений полей. На нём построены история документа и метрики
- Данные пользователей изолированы: чужой документ, шаблон или карточка отвечают 404, как
  несуществующие

## Безопасность

- Вход только по initData, подписанному клиентом MAX: HMAC-SHA256 от токена бота и срок жизни
  строки. Дальше access JWT на 15 минут и refresh-cookie `HttpOnly` с ротацией и отзывом
- Единый формат ошибки `{"detail", "code", "request_id"}` без внутренностей исключений, по
  `request_id` находится строка в логах ядра и gateway
- На проде gateway держит TLS, CSP, лимиты запросов и размера тел, вебхук бота проверяется
  секретом в заголовке. Контейнеры `api`, `bot` и `certbot` идут с read-only FS, `cap_drop ALL` и
  `no-new-privileges`
- В логах нет значений полей документа, сырого initData и токенов

Подробно, вместе с ограничениями, в [docs/SECURITY.md](docs/SECURITY.md)

## Тестовые данные

Смоделированы только реквизиты организаций, для проверки и демонстрации. Они вымышленные, но
сходятся по контрольным суммам ИНН, КПП, ОГРН и ключу расчётного счёта по БИК. БИК и корр. счета
принадлежат настоящим банкам, почта стоит в зарезервированном домене `.example`

- [`test-data.json`](test-data.json): своя организация, клиент, счёт с двумя позициями, ожидаемый
  акт и пример ИНН с неверным контрольным разрядом. Файл генерируется из
  `core.usecases.documents.demo` (`cd core && uv run python -m core.scripts.export_test_data`), те
  же значения стоят в `DATA-API.yaml` и в примерах ниже, тест сверяет их между собой
- Кнопка «Тестовые реквизиты» в формах организации и клиента подставляет тот же набор
- Кнопка «Заполнить демо-данными» на форме документа заполняет все поля случайными вымышленными
  значениями, которые проходят проверку сервера (`web/src/pages/document/mock.ts`). Она видна всем
  на время демонстрации и уйдёт из рабочей версии

## Пошаговая проверка

### В MAX, около двух минут

1. Открыть [@t409_hakaton_max_bot](https://max.ru/t409_hakaton_max_bot), начать диалог и нажать
   «Создать документ» под приветствием
2. Выбрать «Счёт на оплату», нажать «Заполнить»
3. «Заполнить демо-данными» или ввести свои реквизиты и позиции
4. «Проверить документ»: лист как в PDF, с суммой прописью
5. Выбрать PDF или DOCX и нажать «Отправить в чат»: файл приходит в чат с ботом, документ
   появляется во вкладке «Документы»
6. В карточке документа нажать «Сделать акт»: открывается акт с теми же сторонами и позициями

Без мини-аппа: написать боту «Счёт на 120 000 для ООО Ромашка за разработку сайта» и нажать «Всё
верно», бот пришлёт файл (нужен `GIGACHAT_AUTH_KEY` на стенде)

### Через API локально

Вне production ручка `GET /api/v1/dev/init-data` выдаёт подписанный initData тестового
пользователя, по нему выдаётся токен:

```bash
INIT=$(curl -s http://localhost:3090/api/v1/dev/init-data | python3 -c 'import json,sys; print(json.load(sys.stdin)["init_data"])')
TOKEN=$(curl -s -X POST http://localhost:3090/api/v1/auth/max -H 'Content-Type: application/json' \
  -d "{\"init_data\": \"$INIT\"}" | python3 -c 'import json,sys; print(json.load(sys.stdin)["access_token"])')
H="Authorization: Bearer $TOKEN"; J='Content-Type: application/json'; API=localhost:3090/api/v1
```

Шаги повторяют `DATA-API.yaml` (там реквизиты полностью, здесь обязательный минимум). Id указаны
для чистой базы, в остальных случаях их берут из ответов шагов 2-5:

```bash
curl -s $API/health                                                          # 1. состояние
curl -s -H "$H" "$API/templates?slug=invoice"                                # 2. шаблон счёта
curl -s -H "$H" -H "$J" $API/organizations \
  -d '{"name":"ООО «Ромашка»","values":{"inn":"7728417603","bank":"ПАО Сбербанк","bic":"044525225","account":"40702810538000123456"}}'   # 3. своя организация
curl -s -H "$H" -H "$J" $API/counterparties \
  -d '{"name":"ООО «Альфа»","values":{"inn":"5003102144"}}'                  # 4. клиент
curl -s -H "$H" -H "$J" $API/documents \
  -d '{"template_id":1,"organization_id":1,"counterparty_id":1}'             # 5. счёт из шаблона
curl -s -X PATCH -H "$H" -H "$J" $API/documents/1/fields \
  -d '{"values":{"number":{"value":"1"},"date":{"value":"24.09.2026"},"items":{"value":"[{\"name\":\"Подготовка пакета документов\",\"price\":\"100000\"},{\"name\":\"Консультация юриста\",\"quantity\":\"2\",\"unit\":\"ч\",\"price\":\"10000\"}]"}}}'   # 6. позиции
curl -s -X POST -H "$H" -H "$J" -d '{"format":"docx"}' $API/documents/1/render   # 7. сборка файла
curl -s -X POST -H "$H" -H "$J" -d '{"format":"docx"}' $API/documents/1/send     # 8. отправка в чат
curl -s -H "$H" $API/documents/1/history                                     # 9. путь документа
curl -s -X POST -H "$H" $API/documents/1/act                                 # 10. акт по счёту
curl -s $API/documents                                                       # 11. без токена
curl -s -H "$H" -H "$J" $API/organizations -d '{"name":"ООО «Ромашка»","values":{"inn":"7728417604"}}'   # 12. неверный ИНН
```

С ключом `GIGACHAT_AUTH_KEY` поля заполняются и из файла. Файл уходит сырым телом запроса, а
`Content-Type` равен типу файла:

```bash
curl -s -X POST -H "$H" -H 'Content-Type: image/jpeg' --data-binary @card.jpg \
  "$API/documents/1/agent/recognize?hint=реквизиты покупателя"
curl -s -X POST -H "$H" -H 'Content-Type: audio/ogg' --data-binary @voice.ogg $API/documents/1/agent/voice
curl -s -X POST -H "$H" -H 'Content-Type: application/pdf' --data-binary @card.pdf $API/requisites/recognize
```

Распознанное приходит с `source: "ocr"`, строкой-источником `fragment` и `confirmed: false`.
Документ станет готовым после `POST /documents/1/confirm`

## Ожидаемое поведение

| Шаг | Ответ                                                                                                           |
| --- | --------------------------------------------------------------------------------------------------------------- |
| 1   | 200 `{"status":"ok","checks":{"database":"ok","redis":"ok","events_worker":"ok"}}`, при деградации 503          |
| 3-4 | 201 и карточка, первая организация становится основной                                                          |
| 5   | 201, счёт `draft`: стороны подставлены из карточек, дата сегодняшняя, номер следующий, в `missing` поле `items` |
| 6   | 200, `ready: true`, `errors: []`, в предпросмотре «120 000,00» и «Сто двадцать тысяч рублей 00 копеек»          |
| 7   | 200, имя файла, размер и `stale: false`                                                                         |
| 8   | 202 и UUID события, бот присылает файл в чат                                                                    |
| 9   | факты `created`, `ready`, `rendered`, `sent`, после ответа бота `delivered`                                     |
| 10  | 201, акт: стороны, позиции и сумма из счёта, номер и дата новые                                                 |
| 11  | 401 `auth.missing_token`                                                                                        |
| 12  | 422 `organization.invalid` с текстом, какое поле не прошло, организация не сохраняется                          |

- Ошибочное значение поля документа не сохраняется: поле остаётся пустым, а в `errors` приходит
  код вида `field.inn_invalid` с текстом для человека
- Сборка с ошибкой в значении или с неподтверждённым распознанным значением отвечает 409
  `document.not_ready`. Пустые необязательные поля сборку не держат, в файле на их месте линии
- Без настоящего `MAX_BOT_TOKEN` бот не стартует и событие ждёт в очереди. У учётки проверяющих на
  проде выдуманный MAX-id, поэтому в истории её счёта появится `delivery_failed`, а не `delivered`

## Известные ограничения

- PDF собирается только в образе с `WITH_PDF=true`. Без LibreOffice сборка PDF отвечает 503
  `render.pdf_unavailable`, картинка листа 503 `preview.unavailable`, DOCX работает всегда
- Помощник включается ключом `GIGACHAT_AUTH_KEY`. Без него его ручки отвечают 503
  `agent.unavailable`, а бот отвечает, что помощник выключен
- Распознаются фото JPG, PNG, WEBP, BMP, TIFF, файлы PDF и DOCX до 10 МБ и голосовые OGG, MP3,
  M4A, WEBM, WAV. Скан без текстового слоя помощник читает по картинкам первых страниц
- Документ по своему файлу сохраняет оформление у DOCX. Из PDF переносится только текст, XLS,
  XLSX и старый DOC не принимаются
- Паспортные поля есть только в договорах с физлицами и самозанятым и в акте приёма-передачи
  имущества, с фото они не распознаются и заполняются руками
- Таблица позиций (до 100 строк) есть в счетах, в трёх актах на работы и услуги и в «КП: с
  позициями». В обычном и кратком КП одна строка на весь предмет
- Проектов и версий документа нет: «На основе этого» делает копию, а не версию
- Файлы лежат на диске контейнера, объектного хранилища и чистки сирот нет
- Открытые вопросы и бэклог находятся в [docs/PRODUCT.md](docs/PRODUCT.md) и
  [docs/FLOWS.md](docs/FLOWS.md)

## Остановка и перезапуск

```bash
docker compose stop        # остановить, данные и тома сохраняются
docker compose up -d       # поднять снова
docker compose down        # снять стек, тома остаются
docker compose down -v     # снять вместе с данными PostgreSQL и Redis
```

Миграции применяет процесс API при старте, отдельного шага нет. Консоль стенда `./maxapp` даёт
логи, состояние контейнеров, psql, redis-cli, миграции и проверки, `./maxapp help` показывает
список команд

## Проверки качества

```bash
./maxapp check     # ruff, import-linter, pytest, eslint, tsc, dependency-cruiser, vitest
./maxapp audit     # известные уязвимости: pnpm audit и pip-audit по uv.lock
```

| ------------------------- | ------------------------------------------------------------------- |
| Поведение ядра            | pytest: API, сценарии, домен, файлы, события, миграции              |
| Бот и мини-апп            | vitest и компилятор TypeScript                                      |
| Границы сервисов и слоёв  | import-linter, dependency-cruiser                                   |

По отдельности: `cd core && uv run pytest -q` и `npx -y pnpm@12.4.2 test`. Те же проверки ставятся

## Собственный API

- Адрес: `https://project-documents-max.ru`, префикс `/api/v1`. Swagger и `openapi.json` отдаются
  только вне production (локально на `/api/v1/docs`), на проде схема лежит в репозитории
- OpenAPI 3.1 в [contracts/openapi.json](contracts/openapi.json) генерируется из кода
  (`cd core && uv run python -m core.scripts.export_openapi`), из него же генерируются типы
  мини-аппа
- Обязательные проверки в [DATA-API.yaml](DATA-API.yaml): основной путь от реквизитов до акта,
  отправка в чат, путь документа и отказы (без токена, неверный ИНН, несуществующий документ).
  Официальный валидатор DATA-API 1.0 проходит без замечаний, а сам сценарий с переменными из
  `extract` и cleanup прогоняется против приложения тестом, поэтому устаревшее поле валит наш тест
  раньше проверки жюри
- Роли: `public` (только `/health`) и `user` (вход по initData, затем Bearer-токен).
  Администраторам из `ADMIN_MAX_IDS` открыты `/admin/stats`, `/admin/notify` и
  `/admin/metrics?days=30`: пользователи, документы по видам и форматам, воронка до доставки, доля
  автозаполнения, пойманные ошибки, время сборки и прогоны помощника. В мини-аппе это экран
  «Метрики» в профиле
- Доступ для проверяющих. Обычный токен живёт 15 минут, а initData выдаёт только клиент MAX,
  поэтому оператор выпускает долгий токен роли `user` для отдельной учётки:

  ```bash
  docker compose -f docker-compose.prod.yml exec api python -m core.scripts.issue_reviewer_token --days 365
  docker compose -f docker-compose.prod.yml exec api python -m core.scripts.issue_reviewer_token --revoke
  ```

  `--revoke` удаляет учётку вместе с данными, и токен перестаёт работать сразу. Если прогон
  оборвался до cleanup, повторное создание ответит 422 `*.duplicate_inn`: тогда учётку
  перевыпускают, и она начинает с пустого листа

## Прод

Мини-приложение в MAX открывается по адресу `https://project-documents-max.ru`, поэтому стенд
работает на сервере с публичным IP. Нужны A-запись домена, открытые порты 80 и 443 и `.env` на
сервере, затем `./deploy.sh`: тесты ядра в образе, сертификат Let's Encrypt, снимок БД и подъём
`docker-compose.prod.yml`. Прод-стенд состоит из семи контейнеров: `db`, `redis`, `api`, `bot`,
`gateway`, `certbot`, `db_backup`. Подробности в [docs/DEPLOY.md](docs/DEPLOY.md)
