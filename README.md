# Документы для бизнеса в MAX

Мини-приложение и бот мессенджера MAX, которые готовят типовые документы малого
бизнеса: счёт на оплату, коммерческое предложение, договор оказания услуг.
Владелец выбирает шаблон, отдаёт данные формой или сообщением, проверяет
предпросмотр и получает готовый файл в чат — без возврата к компьютеру и ручной
замены реквизитов. Продукт целиком, бэклог и нерешённые вопросы —
[docs/PRODUCT.md](docs/PRODUCT.md); единый пользовательский путь и нестыковки
макета — [docs/FLOWS.md](docs/FLOWS.md).

Хакатон MAX 2026, трек «Эффективный бизнес», команда 409.

## Основной пользовательский сценарий

1. Пользователь открывает мини-приложение из чата с ботом.
2. Один раз заполняет реквизиты своей компании и карточку контрагента; ИНН,
   ОГРН, БИК и расчётный счёт проверяются контрольными суммами.
3. Выбирает шаблон — стандартный или свой. Стандартных 12, все — бланки DOCX
   по образцам делового оборота: счёт (обычный, на товар, с НДС и
   основанием), КП (на бланке, краткое, с позициями) и договор оказания услуг
   (основной, между юрлицами, между физлицами, с ИП, с самозанятым, типовой).
   Документ собирается в копии бланка: шрифты, табуляция, таблицы и линейки —
   как в образце, сумма печатается и прописью. Свой делается из готового
   документа DOCX или PDF (места для данных находят метки `{{…}}` в файле,
   помощник или правила по линейкам и реквизитам, человек проверяет; из DOCX
   документы собираются с логотипом и оформлением файла), пишется текстом в
   мини-аппе или берётся из стандартного бланка. «Заполнить» сразу открывает
   форму: реквизиты своей компании в ней уже стоят, видно, откуда взято каждое
   значение.

   Документа нет в каталоге — «Создать» → «Изменить свой файл»: договор от
   партнёра, прошлый счёт, анкета. Сервер находит в файле места для данных и
   сразу создаёт документ, где значения — как в файле (`POST /documents/import`);
   человек правит их в той же форме, а файл собирается в копии присланного.
   Шаблон такого документа можно оставить в каталоге («Сохранить как шаблон»).

4. Заполняет оставшиеся поля (клиент, сумма, предмет, сроки) — руками или, как
   в чате с ботом, с фото, голосом или текстом: помощник раскладывает данные по
   полям и возвращает в форму. Затем смотрит предпросмотр: незаполненное видно
   прочерками, ошибки — текстом рядом с полем.
5. Нажимает «отправить»: бот присылает в чат готовый DOCX или PDF с
   сопроводительным текстом, документ остаётся в истории — видно, когда и в
   каком формате он ушёл и дошёл ли до чата. Следующий такой же документ
   делается копией (`POST /documents/{id}/copy` или кнопка «На основе этого»):
   стороны и условия те же, реквизиты свежие, номер и даты — новые.

То же можно сделать прямо в чате с ботом: написать «Счёт на 120 000 для ООО
Ромашка за разработку сайта» — помощник создаст документ, покажет заполненные
значения с кнопкой «Всё верно», а после подтверждения пришлёт файл. Поправки
(«поменяй сумму на 150 000») и вопросы («чего не хватает?») пишутся так же,
а вместо текста можно надиктовать голосовое или прислать фото карточки
предприятия, счёта или договора (JPG, PNG, PDF, DOCX): помощник распознает
реквизиты, покажет, что прочитал, и подставит их только после подтверждения.
Присланный DOCX или PDF можно и «✏️ Изменить»: бот покажет найденные в нём
значения, поправки пишутся сообщением («Покупатель — ООО Ромашка, сумма
150 000»), а готовый файл приходит в оформлении присланного.

## Запуск одной командой

Нужны Docker с compose. Токены и пароли — в `.env`, он не входит в репозиторий.

```bash
cp .env.example .env      # вписать MAX_BOT_TOKEN; по желанию GIGACHAT_AUTH_KEY
docker compose up --build
```

Пароли и секреты `dev-only-…` из `.env.example` локально работают как есть (в
production валидатор их отвергает); без настоящего `MAX_BOT_TOKEN` поднимаются
API и мини-апп, а бот не стартует. Пустой `GIGACHAT_AUTH_KEY` выключает
помощника, остальной сценарий работает.

Локальный стек описан в `compose.yaml` и поднимает пять контейнеров: `db`,
`redis`, `api`, `bot`, `web` (плюс одноразовый `deps`, ставящий Node-зависимости).
Сборка без кеша, не считая загрузки базовых образов, — меньше минуты на образ:
ядро около 40 секунд, образы бота и gateway с мини-аппом для прода — около 50.

| Адрес                               | Что                                                |
| ----------------------------------- | -------------------------------------------------- |
| http://localhost:3090               | мини-апп (vite с HMR; `/api/` проксируется в core) |
| http://localhost:3090/api/v1/docs   | Swagger API                                        |
| http://localhost:3090/api/v1/health | состояние БД, Redis и потребителя событий          |

Бот в локальном стенде работает через long polling, публичный адрес не нужен, но
нужен настоящий `MAX_BOT_TOKEN`: с плейсхолдером MAX отвечает 401. Если тот же бот
уже работает на проде через вебхук, локальный polling не запускается, чтобы не
снять подписку прода (`bot.polling.blocked` в логе): для локальной отладки нужен
второй бот, см. [docs/DEPLOY.md](docs/DEPLOY.md).

## Состав и архитектура

Репозиторий один, сервисов четыре; каждая папка в корне — отдельная деплой-единица
со своим рантаймом и образом.

```
core/       Python 3.14, FastAPI: API мини-аппа, миграции при старте, потребитель событий бота, владелец PostgreSQL
bot/        Node 24, @maxhub/max-bot-api: приветствие, кнопка мини-аппа, доставка готовых файлов в чат
web/        React 19 + Vite + MAX UI: мини-апп (создать · архив · профиль), вход по подписи initData
gateway/    nginx (прод): TLS, /api/ → core, вебхук бота, статика web, лимиты, CSP
contracts/  OpenAPI ядра и JSON Schema событий — единственное общее между сервисами
docs/       продукт, пользовательские пути, архитектура, деплой, логи, платформа MAX
```

Сервисы не импортируют друг друга: общее — только `contracts/` и инфраструктура
(PostgreSQL, Redis). Шов core ↔ bot — Redis Streams с типизированным контрактом:
ядро публикует `document.ready`, бот забирает файл по одноразовому токену и
отправляет вложением. Подробно, вместе с картой модулей и правилами, —
[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Переменные окружения

Все переменные стека описаны в одном реестре `core.config.env_spec`; корневой
`.env.example` генерируется из него и содержит описание, тип и значение по
умолчанию каждой. Обязательный минимум для запуска:

| Переменная       | Зачем                                                       |
| ---------------- | ----------------------------------------------------------- |
| `MAX_BOT_TOKEN`  | токен бота из MasterBot; им же проверяется подпись initData |
| `JWT_SECRET`     | подпись access-токенов, 32+ случайных символа               |
| `DB_PASSWORD`    | пароль PostgreSQL                                           |
| `REDIS_PASSWORD` | пароль Redis                                                |
| `ADMIN_MAX_IDS`  | JSON-массив MAX-id администраторов                          |

Полезные необязательные: `GIGACHAT_AUTH_KEY` (ключ GigaChat API, включает
помощника и распознавание фото и голосовых), `MEDIA_MAX_BYTES` (предел файла на
распознавание, по умолчанию 10 МБ), `MAX_MINI_APP_NAME` (имя мини-аппа для кнопки
`open_app`; без него кнопка не рисуется), `DEV_LOGIN_ENABLED` (вход тестовым
пользователем вне production), `WITH_PDF=true` (собрать образ ядра с LibreOffice
и включить выдачу PDF локально), `PUBLIC_BASE_URL` (нужен боту в режиме webhook).

## Зависимости

Версии зафиксированы локами: `core/uv.lock` (Python, менеджер `uv`) и
`pnpm-lock.yaml` (Node-воркспейсы `bot` и `web`). Основное: FastAPI, SQLAlchemy 2
async, Alembic, redis.asyncio, PyJWT, python-docx, pypdf; TypeScript 5.9,
`@maxhub/max-bot-api`, ioredis, pino, zod, React 19, Vite 8. Инфраструктура:
PostgreSQL 17, Redis 7, nginx 1.27. Сборка PDF использует LibreOffice, который
ставится в образ ядра при `WITH_PDF=true` вместе со шрифтами Liberation,
Carlito и Caladea — метрическими аналогами Times New Roman, Arial, Courier New,
Calibri и Cambria, которыми свёрстаны бланки: PDF переносит строки так же, как
DOCX.

## Внешние сервисы и интеграции

- **MAX Bot API** (`https://platform-api2.max.ru`) — получение апдейтов, отправка
  сообщений и загрузка файлов. Сертификат подписан корнем НУЦ Минцифры, он лежит
  в `bot/certs/` и подключается через `NODE_EXTRA_CA_CERTS`.
- **MAX Bridge** (`https://st.max.ru/js/max-web-app.js`) — мост мини-аппа,
  источник подписанного `initData`.
- **GigaChat API** (`https://api.giga.chat/v1`, токен через
  `https://ngw.devices.sberbank.ru:9443/api/v2/oauth`) — модель помощника и
  распознавания: фото, сканы и голосовые загружаются в хранилище файлов
  GigaChat на один запрос и сразу удаляются. Необязателен: без ключа помощник
  выключен, остальной сценарий работает. Модель только предлагает значения
  полей; проверяет их домен, файл собирает шаблонизатор, отправляет человек.
- **Хранилище файлов MAX** — ядро скачивает по ссылке из апдейта фото, файл или
  голосовое, присланное боту (бот передаёт только ссылку).
- **Let's Encrypt** — сертификат для `DOMAIN` на проде: контейнер `certbot`
  выпускает и продлевает его по http-01, gateway подхватывает новую пару сам.
- Других внешних систем нет: 1С и Госуслуги описаны в планах, но не подключены,
  и их работа нигде не имитируется — все интеграции выше настоящие. Смоделированы
  только вымышленные реквизиты для проверки и демонстрации, см. «Тестовые данные
  и проверка».

## Работа с данными

- **PostgreSQL** (владелец — только `core`): пользователи, refresh-токены,
  шаблоны, свои организации, карточки контрагентов, документы и метаданные
  собранных файлов, журнал фактов по документам (создан, готов, собран,
  отправлен, доставлен, отклонённые значения — без персональных данных) и дни
  активности пользователей. Схемой владеют миграции Alembic, применяются при
  старте API.
- **Redis**: сессии бота, потоки событий между ядром и ботом, одноразовые токены
  на скачивание файла (живут час, сгорают при первом использовании).
- **Диск**: готовые DOCX и PDF в томе `app_data/api` (`DOCUMENTS_DIR`); в базе
  хранится путь, размер и хеш.
- Значения полей документа хранятся вместе с источником (ручной ввод, профиль,
  карточка контрагента, помощник, распознанное фото) — на этом держится
  подсветка в предпросмотре. У распознанного значения хранится ещё строка с фото,
  из которой оно прочитано, и уверенность; само фото нигде не сохраняется.

## Тестовые данные и проверка

Смоделированы в решении только реквизиты организаций — для проверки и
демонстрации; внешние системы ими не подменяются. Реквизиты вымышленные, но
сходятся по контрольным суммам (ИНН, ОГРН, КПП, ключ расчётного счёта по БИК):
придуманные руками счёт и БИК почти никогда не сходятся. БИК и корр. счета —
настоящих банков, почта — в зарезервированном домене `.example`.

- [`test-data.json`](test-data.json) — тестовые данные проверки API: своя
  организация, клиент и счёт с двумя позициями. Те же значения стоят в
  [`DATA-API.yaml`](DATA-API.yaml) и в примерах ниже; файл генерируется из
  `core.usecases.documents.demo` (`cd core && uv run python -m core.scripts.export_test_data`).
- Кнопка «Тестовые реквизиты» в формах организации и клиента и
  `GET /api/v1/dev/requisites` (вне production) подставляют тот же набор.
- Кнопка «Заполнить демо-данными» на форме документа видна всем на время
  демонстрации: заполняет все поля случайными вымышленными значениями, которые
  проходят проверку сервера (`web/src/pages/document/mock.ts`). В рабочей версии
  её не будет.

Реквизиты в присланных образцах (рыбах) тоже часто вымышленные — такой ИНН или
счёт при «Изменить свой файл» не подставляется, а ошибка видна у поля.

Вне production ручка `GET /api/v1/dev/init-data` (включается `DEV_LOGIN_ENABLED`)
выдаёт подписанный initData тестового пользователя, поэтому мини-апп в браузере
входит сам. Для запросов к API вручную:

```bash
INIT=$(curl -s http://localhost:3090/api/v1/dev/init-data | python3 -c 'import json,sys; print(json.load(sys.stdin)["init_data"])')
TOKEN=$(curl -s -X POST http://localhost:3090/api/v1/auth/max -H 'Content-Type: application/json' \
  -d "{\"init_data\": \"$INIT\"}" | python3 -c 'import json,sys; print(json.load(sys.stdin)["access_token"])')
```

Пошаговый сценарий проверки — тот же, что в `DATA-API.yaml` (там реквизиты
полностью, здесь — обязательный минимум). Id в примерах — для чистой базы; в
остальных случаях их берут из ответов шагов 2–5:

```bash
curl -s localhost:3090/api/v1/health                                          # 1. состояние сервиса
curl -s -H "Authorization: Bearer $TOKEN" 'localhost:3090/api/v1/templates?slug=invoice'   # 2. шаблон счёта
curl -s -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":"ООО «Ромашка»","values":{"inn":"7728417603","bank":"ПАО Сбербанк","bic":"044525225","account":"40702810538000123456"}}' \
  localhost:3090/api/v1/organizations                                         # 3. своя организация
curl -s -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":"ООО «Альфа»","values":{"inn":"5003102144"}}' \
  localhost:3090/api/v1/counterparties                                        # 4. карточка клиента
curl -s -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"template_id":1,"organization_id":1,"counterparty_id":1}' \
  localhost:3090/api/v1/documents                                             # 5. счёт из шаблона
curl -s -X PATCH -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"values":{"number":{"value":"1"},"date":{"value":"24.09.2026"},"items":{"value":"[{\"name\":\"Подготовка пакета документов\",\"price\":\"100000\"},{\"name\":\"Консультация юриста\",\"quantity\":\"2\",\"unit\":\"ч\",\"price\":\"10000\"}]"}}}' \
  localhost:3090/api/v1/documents/1/fields                                    # 6. номер, дата, позиции
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"format":"docx"}' localhost:3090/api/v1/documents/1/render             # 7. сборка файла
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"format":"docx"}' localhost:3090/api/v1/documents/1/send               # 8. отправка в чат MAX
curl -s -H "Authorization: Bearer $TOKEN" localhost:3090/api/v1/documents/1/history   # 9. путь документа
```

С ключом `GIGACHAT_AUTH_KEY` поля заполняются и из файла — он уходит сырым
телом запроса, `Content-Type` — тип файла:

```bash
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: image/jpeg' \
  --data-binary @card.jpg 'localhost:3090/api/v1/documents/1/agent/recognize?hint=реквизиты покупателя'
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: audio/ogg' \
  --data-binary @voice.ogg localhost:3090/api/v1/documents/1/agent/voice
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/pdf' \
  --data-binary @card.pdf localhost:3090/api/v1/requisites/recognize   # реквизиты для формы карточки
```

Распознанное приходит со `source: "ocr"`, строкой-источником `fragment` и
`confirmed: false`: документ станет готовым после `POST /documents/1/confirm`.

## Ожидаемое поведение

- Шаг 1 отвечает `{"status":"ok","checks":{"database":"ok","redis":"ok","events_worker":"ok"}}`;
  при деградации — 503 с тем же телом.
- Шаги 3 и 4 отвечают 201 и карточкой; первая организация становится основной.
  Реквизит с неверной контрольной суммой не сохраняется: 422
  `organization.invalid` с текстом, какое поле не прошло.
- Шаг 5 возвращает счёт со статусом `draft`: реквизиты продавца и покупателя уже
  подставлены из карточек, дата — сегодняшняя, в `missing` — `number` и `items`.
- Шаг 6 переводит документ в `ready: true` с пустым `errors`; итог и сумма
  прописью считаются из позиций (100 000 + 2 × 10 000): в предпросмотре
  «120 000,00» и «Сто двадцать тысяч рублей 00 копеек».
- Шаг 7 возвращает имя файла, размер и `stale: false`. Пустые необязательные
  поля сборку не держат — в файле на их месте линии; ошибка в значении или
  непроверенное распознанное значение — 409 `document.not_ready`.
- Шаг 8 отвечает 202 и UUID события. Шаг 9 показывает путь документа
  `created → ready → rendered → sent`; когда бот с настоящим `MAX_BOT_TOKEN`
  присылает файл в чат MAX, к нему добавляется `delivered`. Без токена бот не
  стартует, и событие ждёт в очереди.
- Ошибочное значение поля документа не сохраняется: поле остаётся пустым, а в
  `errors` приходит код вида `field.inn_invalid` с текстом для пользователя.

## Известные ограничения

- В мини-приложении нет проектов и версий документа; без доступа к микрофону
  голосовое выбирают готовым файлом. Шаблон из PDF переносит только текст, а скан
  без текстового слоя не принимается — см. [docs/FLOWS.md](docs/FLOWS.md), раздел
  «Вопросы на решение».
- PDF собирается только в образе с `WITH_PDF=true`; без LibreOffice ручка
  отвечает 503 `render.pdf_unavailable`, DOCX работает всегда.
- Помощник на GigaChat (заполнение из сообщения, фото, скана или голосового,
  ответы по документу, сопроводительное письмо, реквизиты с фото для карточки)
  включается ключом `GIGACHAT_AUTH_KEY`; без ключа его ручки отвечают 503
  `agent.unavailable`, а бот в чате отвечает, что помощник выключен.
- Распознаются фото JPG/PNG (а также WEBP, BMP, TIFF), PDF и DOCX до 10 МБ и
  голосовые OGG/MP3/M4A/WEBM/WAV. Паспортные поля есть только в договорах с
  физлицами и самозанятым и с фото не распознаются — до решения по правовому
  минимуму их заполняют руками.
- Таблица позиций (до 100 строк, итог и сумма прописью считаются из них) есть
  только в счетах; в КП одна строка на весь предмет — с количеством и единицей.
- Документ по своему файлу сохраняет оформление у DOCX; из PDF переносится
  только текст, XLS/XLSX и старый DOC не принимаются — их нужно сохранить как
  DOCX. Без помощника места находят метки `{{…}}` и правила (линейки с подписью,
  пустые ячейки-линейки, реквизиты, даты), и названия полей у них проще.
- Файлы лежат на диске контейнера; объектного хранилища и чистки сирот нет.
- Сопроводительный текст по умолчанию служебный; письмо от помощника
  запрашивается отдельно и уходит в чат только после того, как человек его
  отправил.

## Остановка и повторный запуск

```bash
docker compose stop              # остановить, данные и тома сохраняются
docker compose up -d             # поднять снова
docker compose down              # снять стек (тома остаются)
docker compose down -v           # снять вместе с данными PostgreSQL и Redis
```

Миграции применяет сам процесс API при старте, отдельного шага нет. Консоль
стенда — `./maxapp` (логи, состояние, psql, redis, миграции, проверки).

## Проверки

```bash
./maxapp check     # ruff, import-linter, pytest, eslint, tsc, dependency-cruiser, vitest
```

По отдельности: `cd core && uv run pytest -q`, `npx -y pnpm@12.4.2 test`.

## Собственный API

- Адрес в проде: `https://project-documents-max.ru`, префикс `/api/v1`.
- OpenAPI 3.1: [contracts/openapi.json](contracts/openapi.json), генерируется из
  кода (`cd core && uv run python -m core.scripts.export_openapi`).
- Обязательные проверки для технической оценки: [DATA-API.yaml](DATA-API.yaml),
  тестовые данные к ним — [test-data.json](test-data.json). Официальный
  валидатор DATA-API 1.0 проходит без замечаний, а сам сценарий — запросы по
  порядку, переменные из `extract`, cleanup — прогоняется против приложения
  тестом `core/tests/api/test_data_api.py` в `./maxapp check`: устаревшее поле
  в теле запроса валит тест, а не проверку жюри.
- Роли: `public` (только `/health`) и `user` — вход по подписанному initData,
  дальше Bearer-токен; администраторам (`ADMIN_MAX_IDS`) открыты `/admin/stats`,
  `/admin/notify` и `/admin/metrics?days=30` — метрики по дням для графиков:
  пользователи (всего, новые, активные за день и неделю), документы по видам и
  форматам, воронка до доставки, доля автозаполнения, пойманные ошибки по кодам,
  время от создания до отправки, доставки ботом и время сборки файла. В
  мини-аппе они же на экране «Метрики» (Профиль → «Метрики»).
  Учётные данные передаются отдельным каналом, в репозитории их нет.
- Доступ для проверяющих: у них нет клиента MAX, а обычный токен живёт 15 минут,
  поэтому токен роли `user` выпускает оператор на срок проверки (до 30 дней) —
  для отдельной учётки, чтобы её документы не смешивались с настоящими:

  ```bash
  docker compose -f docker-compose.prod.yml exec api python -m core.scripts.issue_reviewer_token --days 14
  docker compose -f docker-compose.prod.yml exec api python -m core.scripts.issue_reviewer_token --revoke
  ```

  `--revoke` удаляет учётку вместе с её данными, токен перестаёт работать сразу.
  Сценарий создаёт организацию и клиента, а cleanup их удаляет; если прогон
  оборвался до cleanup, повторное создание ответит 422 `*.duplicate_inn` —
  тогда учётку перевыпускают (`--revoke`, затем `--days 14`), и она начинает с
  пустого листа.

## Прод

Мини-приложение в MAX открывается по адресу `https://project-documents-max.ru`,
поэтому стенд живёт на сервере с публичным IP, а не на локальной машине. Нужно:
A-запись домена на IP сервера, открытые порты 80 и 443, `.env` на сервере, затем
`./deploy.sh` — прогон тестов ядра в образе, выпуск сертификата Let's Encrypt,
снимок БД, подъём `docker-compose.prod.yml`. Прод-стенд — семь контейнеров: `db`,
`redis`, `api`, `bot`, `gateway`, `certbot`, `db_backup`. Подробности, список
обязательных переменных и запуск с домашнего компьютера —
[docs/DEPLOY.md](docs/DEPLOY.md).
