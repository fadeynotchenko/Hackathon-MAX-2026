# Архитектура

Один репозиторий, четыре сервиса: `core`, `bot`, `web`, `gateway`. Они едут одним
compose-стеком, но границы между ними микросервисные: свой рантайм, свой образ и
healthcheck, никаких импортов друг из друга. Общее только `contracts/` и
инфраструктура (PostgreSQL, Redis). Всё, что описано ниже как правило, проверяется
машинно: линтерами импортов, тестами-замками и pre-commit

## Сервисы

| Сервис      | Стек                                | Отвечает за                                                            |
| ----------- | ----------------------------------- | ---------------------------------------------------------------------- |
| `core`      | Python 3.14, FastAPI, SQLAlchemy 2  | API мини-аппа, документы, помощник, миграции, потребитель событий бота |
| `bot`       | Node 24, `@maxhub/max-bot-api`, zod | диалог в чате MAX, кнопка мини-аппа, доставка готовых файлов           |
| `web`       | React 19, Vite, `@maxhub/max-ui`    | мини-апп: «Создать», «Документы», «Профиль», вход по подписи initData  |
| `gateway`   | nginx 1.27 (только прод)            | TLS, статика `web`, `/api/` в `core`, вебхук бота, лимиты, CSP         |
| `contracts` | OpenAPI 3.1 и JSON Schema           | единственное общее между сервисами, генерируется из кода `core`        |

Владелец PostgreSQL один: `core`. Бот в базу не ходит, всё нужное он получает
событиями через Redis

## Потоки данных

```
  Клиент MAX ──initData──▶ web (статика) ──/api/v1──▶ gateway ──▶ core ──▶ PostgreSQL
                                                                    │  └──▶ диск: DOCX и PDF
                                                                    ├──▶ GigaChat (помощник, фото, голос)
                                                                    ├──▶ DaData (подсказки реквизитов)
                                                                    └──▶ хранилище MAX (вложения по ссылке)

  MAX ──webhook/polling──▶ bot ──XADD──▶ Redis Stream to_core ──▶ core: воркер событий
                            ▲                                         │
                            └─XREADGROUP── Redis Stream to_bot ◀─XADD─┘ (ответы помощника, document.ready)
```

Путь документа до чата:

1. Мини-апп вызывает `POST /documents/{id}/send`. Ядро собирает файл, кладёт в
   Redis одноразовый токен скачивания (час, сгорает при первом использовании) и
   публикует `document.ready` в стрим бота. Ответ 202 с UUID события
2. Бот читает событие, скачивает файл по токену
   (`GET /documents/download/{token}`) и отправляет вложением в личный чат
3. Бот отвечает событием `bot.document_delivery` с UUID исходного события и
   исходом `delivered` или `failed`. Ядро пишет факт в журнал документа

Вложение, присланное боту (фото, скан, голосовое), идёт по шву ссылкой
(`bot.attachment`), а не байтами: стрим не файловое хранилище, файл ядро скачивает
само (`core.files.inbound`)

## Контракты между сервисами

| Граница       | Контракт                                                                                         | Где проверяется                                              |
| ------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------ |
| core и web    | `contracts/openapi.json`, из него `web/src/api/schema.d.ts`                                      | `core/tests/repo/test_generated_artifacts.py`, компилятор TS |
| core и bot    | `core.events.contracts`, из него `contracts/events.schema.json`, zod в `bot/src/events/codec.ts` | тот же замок и `bot/src/events/codec.test.ts`                |
| bot и gateway | HTTP-вебхук MAX на `${BOT_WEBHOOK_PATH}` с секретом в заголовке                                  | SDK бота сверяет секрет, nginx пускает только этот путь      |

Правила изменения контрактов описаны в [contracts/README.md](../contracts/README.md)

Запреты на импорты:

- `bot/src` и `web/src` не импортируют `core/` и друг друга (`.dependency-cruiser.cjs`:
  `services-share-only-contracts`, `bot-and-web-independent`)
- Python в `core` импортирует только пакет `core` (import-linter, `root_package = core`)
- образ `core` собирается из `./core` и физически не видит другие сервисы
  (`test_docs_sync.py::test_core_build_context_is_isolated`)

## Слои core

```
               ┌─────────────┐   транспорт: роутеры, middleware, lifespan
               │    api/     │   (миграции, воркер событий); разбирает вход,
               └──────┬──────┘   зовёт сценарий, отдаёт ответ
                      ▼
               ┌─────────────┐   сценарии: auth, users, documents, agent, admin;
               │  usecases/  │   функции с явными session, cfg, now,
               └──────┬──────┘   результат: frozen dataclass
     ┌─────────┬──────┴──┬─────────┬─────────┐
     ▼         ▼         ▼         ▼         ▼
 ┌───────┐ ┌───────┐ ┌───────┐ ┌───────┐ ┌─────────┐
 │events/│ │  db/  │ │files/ │ │ llm/  │ │suggest/ │   адаптеры, друг о друге не знают
 └───┬───┘ └───┬───┘ └───┬───┘ └───┬───┘ └────┬────┘
     └─────────┴────┬────┴─────────┴──────────┘
                    ▼
               ┌─────────────┐
               │    logs/    │   структурированные логи
               └──────┬──────┘
             ┌────────┴────────┐
             ▼                 ▼
       ┌───────────┐     ┌───────────┐
       │  config/  │     │  domain/  │   конфиги и чистый домен без I/O
       └───────────┘     └───────────┘
```

| Слой       | Что внутри                                                                                   |
| ---------- | -------------------------------------------------------------------------------------------- |
| `api`      | роутеры FastAPI, схемы OpenAPI, обработчики ошибок, таймауты, request_id, воркер событий     |
| `usecases` | сценарии: вход и сессии, профиль, шаблоны, документы, акты, помощник, метрики администратора |
| `events`   | шов с ботом: конверт, контракты событий, публикация и потребление Redis Streams              |
| `db`       | модели SQLAlchemy, репозитории, движок, миграции Alembic, клиент Redis                       |
| `files`    | сборка DOCX по бланку, PDF через LibreOffice, хранение, вложения, подпись и печать           |
| `llm`      | порт модели (с вложениями) и адаптер GigaChat                                                |
| `suggest`  | порт подсказок реестров и адаптер DaData                                                     |
| `logs`     | JSON-логи с request_id и user_id из contextvars                                              |
| `config`   | реестр переменных окружения `env_spec`, конфиги, валидатор production                        |
| `domain`   | initData, поля и типы документов, реквизиты с контрольными суммами, сумма прописью, ошибки   |

Контракт `layers` в `core/pyproject.toml` (`[tool.importlinter]`): верхний слой
импортирует любой нижний, слои в одной строке через `|` независимы. `scripts/`
(инструменты разработчика и оператора) вне контракта. Проверка:
`cd core && uv run lint-imports`, тот же вызов в pre-commit и
`core/tests/repo/test_import_contracts.py`

Граница `usecases` и `api` проходит по dataclass-результатам: ORM-объект в роутер
не попадает, поэтому ленивая загрузка вне сессии невозможна по построению

| `DocumentEvent`, `UserActivityDay` | `core.db.models`                            | журнал фактов: только пополняется, основа истории и метрик |

| `UserProfileSchema` и прочие       | `core.api.schemas`                          | wire-контракт OpenAPI, из него генерируются TS-типы        |

## Обработка ошибок и устойчивость

**Единый формат ошибки.** Любой отказ API приходит как
`{"detail": str, "code": str, "request_id": str}` (`core.api.error_handlers`):
`detail` мини-апп показывает как есть, `code` нужен для ветвления на клиенте и
поиска в логах. Ошибка валидации запроса добавляет `errors` с разбором pydantic.
Необработанное исключение отдаёт 500 `internal` без внутренностей, стек уходит в
лог под тем же `request_id`

| Код | Когда                                                                        |
| --- | ---------------------------------------------------------------------------- |
| 401 | нет или истёк токен, неверная подпись initData                               |
| 403 | не администратор, запрос с чужого сайта к ручкам на cookie                   |
| 404 | объекта нет или он чужой: разницу наружу не видно                            |
| 409 | документ не готов к сборке или отправке, акт по неподходящему виду документа |
| 413 | файл больше предела (`MEDIA_MAX_BYTES`, по умолчанию 10 МБ)                  |
| 415 | тип файла не поддерживается                                                  |
| 422 | реквизит не прошёл контрольную сумму, неверное тело запроса, повтор ИНН      |
| 502 | модель ответила ошибкой или неразборчиво                                     |
| 503 | помощник выключен, PDF недоступен без LibreOffice, деградация в `/health`    |
| 504 | запрос не уложился в серверный таймаут                                       |

**Значения полей.** Неверное значение поля документа не сохраняется: поле остаётся
пустым, в `errors` приходит код вида `field.inn_invalid` с текстом для человека.
Значения от помощника или с фото ждут подтверждения (`confirmed: false`), до
него сборка отвечает 409 `document.not_ready`

**Таймауты.** У каждой внешней зависимости свой срок, и он короче общего, чтобы
человек видел понятный ответ, а не обрыв:

| Где                                            | По умолчанию                 |
| ---------------------------------------------- | ---------------------------- |
| запрос API (`API_REQUEST_TIMEOUT_SECONDS`)     | 30 с, затем 504              |
| запрос с файлом (`API_UPLOAD_TIMEOUT_SECONDS`) | 85 с                         |
| запрос к БД (`DB_STATEMENT_TIMEOUT_MS`)        | 30 с                         |
| GigaChat текстом и с файлом                    | 20 с и 45 с                  |
| DaData                                         | 5 с                          |
| конвертация в PDF                              | 60 с                         |
| скачивание вложения из MAX                     | 30 с                         |
| `proxy_read_timeout` gateway                   | 60 с, на тяжёлых ручках 90 с |

**Health.** `GET /api/v1/health` проверяет БД, Redis и живость воркера событий.
Если что-то не `ok`, ответ 503 со статусом `degraded` и тем же телом:
healthcheck compose видит деградацию по коду ответа

**Очередь LibreOffice.** Конвертации в PDF идут не больше двух одновременно
(`core.files.pdf`, семафор на цикл событий): параллельные процессы LibreOffice
падали с «Cannot fork». Остальные запросы ждут своей очереди

**Миграции.** Применяются при старте API под advisory-lock PostgreSQL, поэтому
несколько воркеров не гоняются за одной схемой

## Протокол потребителя событий

Обе стороны (Python `core.events.bus.consume_stream`, запускаемый из
`core.api.events_worker`, и TS `bot/src/events/consumer.ts`) реализуют один цикл:
XAUTOCLAIM зависших у упавших потребителей, XREADGROUP новых, обработчик, XACK.
Конверт `{id, v, type, payload, ts, source}`

| Ситуация                                   | Что происходит                                    |
| ------------------------------------------ | ------------------------------------------------- |
| битый конверт, невалидный payload          | подтверждается сразу: повтор не поможет           |
| отказ домена                               | подтверждается сразу                              |
| временная ошибка                           | остаётся pending и переигрывается                 |
| пять неудачных доставок (`max_deliveries`) | подтверждается с записью `events.handler.dropped` |

**Идемпотентность.** Отметка по `Event.id` в Redis в два шага: «в работе» на три
минуты и «сделано» на неделю. Повтор события, которое ещё «в работе», остаётся
pending: если процесс убили посреди ответа модели, повтор после истечения отметки
выполнит работу. Нажатие кнопки бота вдобавок сверяется по паре «пользователь и
payload» в окне 5 секунд: двойное нажатие «Прислать PDF» приходит двумя событиями
с разными id

**Параллельность.** Воркер ядра обрабатывает до четырёх событий одновременно, с
ключом очереди `max_user_id`: реплики одного пользователя идут строго по порядку,
разных пользователей одновременно, и чужое распознавание фото не задерживает
ответ. События в работе продлеваются (`XCLAIM … JUSTID` сбрасывает простой, не
трогая счётчик доставок), поэтому долгий вызов модели не выглядит зависшим для
соседнего процесса

## Контракты TypeScript

Правила `.dependency-cruiser.cjs`:

- `bot/src` и `web/src` не импортируют `core/` и друг друга
- в боте `config`, `logger`, `session`, `events`, `health` не импортируют `handlers`
  и `keyboards`: зависимости направлены от сценариев к инфраструктуре
- в мини-аппе `src/max` (мост WebApp) лист, `src/api` не знает о React-дереве
- циклы и dev-зависимости в прод-коде запрещены

## Тесты

| Набор                            | Сколько   | Что проверяет                                                              |
| -------------------------------- | --------- | -------------------------------------------------------------------------- |
| pytest ядра (`core/tests`)       | около 550 | домен, сценарии, API на SQLite и fakeredis, файлы DOCX и PDF, адаптеры     |
| vitest бота и мини-аппа          | около 265 | обработчики бота, кодек событий, экраны и формы мини-аппа                  |
| сценарий DATA-API                | 1 файл    | `core/tests/api/test_data_api.py` гоняет `DATA-API.yaml` против приложения |
| замки репозитория (`tests/repo`) | 6 файлов  | документация, сгенерированные артефакты, импорты, инфраструктура, стиль    |

Сценарий DATA-API проходит запросы по порядку, с переменными из `extract`,
токеном учётки проверяющих и cleanup, и сравнивает каждый ответ с `expected`.
Сам файл сверяется с официальной схемой организаторов
(`core/tests/api/DATA-API.schema.json`, скопирована без правок), а пути и методы с
`contracts/openapi.json`. Повторный прогон той же учёткой проходит так же, как
первый

Замки `core/tests/repo`:

- `test_docs_sync.py`: слои в этом документе, обязательные переменные в DEPLOY,
  команды запуска в README, изоляция контекста сборки `core`
- `test_generated_artifacts.py`: `openapi.json`, `events.schema.json`,
  `.env.example`, `test-data.json` и TS-типы не отстали от кода
- `test_import_contracts.py`: import-linter и dependency-cruiser зелёные
- `test_infra_config.py`: состав стеков, hardening контейнеров, лимиты и маршруты
  nginx, CSP, запуск не от root, корень Минцифры в образе бота
- `test_no_ai_markers.py`: в коде и документах нет маркеров сгенерированного текста
- `test_markdown_style.py`: в документации нет длинных тире и эмодзи

Все проверки разом: `./maxapp check` (ruff, import-linter, pytest, eslint, tsc,
dependency-cruiser, vitest). Перед выкаткой `deploy.sh` гоняет pytest ядра внутри
тестового образа, красные тесты останавливают деплой. Качество помощника на
настоящей модели меряет отдельный набор из 19 примеров:
`uv run python -m core.scripts.agent_eval`
