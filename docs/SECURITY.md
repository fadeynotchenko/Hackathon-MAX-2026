# Безопасность и работа с данными

Что защищено, где это в коде и чем проверяется. Только то, что реально работает
на стенде

## Вход и сессии

```
 Клиент MAX ──initData (HMAC)──▶ POST /auth/max ──▶ access JWT (15 мин) в ответе
                                                  └▶ refresh (30 дней) в cookie
 Мини-апп ──Bearer access──▶ /api/v1/...          истёк access ──▶ POST /auth/refresh
```

| Механизм               | Как устроен                                                                                                                   | Где                          |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------- | ---------------------------- |
| вход                   | только по initData, подписанному клиентом MAX: HMAC-SHA256 от токена бота, сравнение `hmac.compare_digest`                    | `core.domain.initdata`       |
| срок initData          | `auth_date` не старше `INIT_DATA_MAX_AGE_SECONDS` (час)                                                                       | `core.domain.initdata`       |
| access-токен           | JWT, подпись `JWT_SECRET`, живёт `ACCESS_TOKEN_TTL_SECONDS` (15 минут), только в памяти мини-аппа                             | `core.usecases.auth.tokens`  |
| refresh-токен          | случайные 48 байт, в базе хранится только SHA-256, cookie `HttpOnly`, путь `/api/v1/auth`, в проде `Secure` и `SameSite=None` | `core.api.routers.auth`      |
| ротация                | каждый `/auth/refresh` выдаёт новый refresh и гасит старый                                                                    | `core.usecases.auth.session` |
| повтор старого refresh | считается кражей: отзывается всё семейство токенов, событие `auth.refresh.reuse_detected`                                     | `core.usecases.auth.session` |
| выход                  | `/auth/logout` отзывает семейство и очищает cookie                                                                            | `core.usecases.auth.session` |
| запрос с чужого сайта  | ручки на cookie отвечают 403 `auth.cross_site` на `Sec-Fetch-Site: cross-site`                                                | `core.api.routers.auth`      |

`SameSite=None` нужен, потому что веб-клиент MAX открывает мини-апп во фрейме со
своего домена. Защиту от подделки запроса тогда держит проверка `Sec-Fetch-Site`

Пользователь читается из базы на каждый запрос: удалённая учётка теряет доступ
сразу, даже с живым access-токеном

## Роли

| Роль          | Что доступно                                               |
| ------------- | ---------------------------------------------------------- |
| `public`      | только `GET /api/v1/health`                                |
| `user`        | свои документы, шаблоны, организации, клиенты, помощник    |
| администратор | вдобавок `/admin/stats`, `/admin/notify`, `/admin/metrics` |

Администратор определяется по `ADMIN_MAX_IDS` на каждом запросе: убрать MAX-id из
переменной и перезапустить api значит снять права. Не администратору эти ручки
отвечают 403 `auth.not_admin`

**Токен проверяющих.** `core.scripts.issue_reviewer_token` выпускает долгий токен
роли `user` (до 365 дней) только для отдельной учётки с выдуманным MAX-id
`409000001`, без прав администратора. Токен видит только данные этой учётки.
`--revoke` удаляет учётку с её данными, токен перестаёт работать сразу. В
репозитории токена нет, `DATA-API.yaml` проверяется на отсутствие JWT тестом

**Dev-вход.** `GET /api/v1/dev/init-data` и `/dev/requisites` подключаются только
при `DEV_LOGIN_ENABLED=true` вне production. В production валидатор окружения не
даёт стартовать с этим флагом

## Изоляция данных пользователей

Каждый запрос к документам, шаблонам, организациям и клиентам фильтруется по
`user_id` в репозитории (`core.db.repositories`). Чужой объект неотличим от
несуществующего: ответ 404 с тем же кодом, что для удалённого. Свои шаблоны
пользователя видит только он, стандартные общие и только для чтения (правка
стандартного шаблона отвечает 403)

## Проверка входных данных

| Что              | Как                                                                                      |
| ---------------- | ---------------------------------------------------------------------------------------- |
| тела запросов    | схемы pydantic, неверный тип или формат поля даёт 422 `validation`                       |
| строки           | `PrintableStr` отбрасывает управляющие и невидимые символы, длины ограничены схемой      |
| id               | целые от 1 до 2^63-1 в пути и теле                                                       |
| реквизиты        | ИНН, КПП, ОГРН, БИК, счёт с ключом по БИК проверяются контрольными суммами до сохранения |
| файлы            | тип по первым байтам, а не по заголовку или расширению (`core.domain.media`)             |
| размер файла     | `MEDIA_MAX_BYTES` (10 МБ), заявленный `Content-Length` проверяется до чтения тела, 413   |
| типы файлов      | JPG, PNG, WEBP, BMP, TIFF, PDF, DOCX, OGG, MP3, M4A, WEBM, WAV; прочее 415               |
| подпись и печать | картинка пересобирается в PNG не больше 800 пикселей, битая или пустая отклоняется       |
| вложения из MAX  | скачиваются только по https, с таймаутом                                                 |
| SQL              | только параметризованные запросы SQLAlchemy                                              |
| HTML в чате      | всё от человека и модели экранируется перед отправкой                                    |

Значения, предложенные моделью, проходят те же проверки домена, что и ручной ввод,
и ждут подтверждения человека. Значение без опоры в сообщении пользователя
помощник отбрасывает

## Секреты

- все секреты только в `.env`, он в `.gitignore` и в `.dockerignore` корня. В репозитории
  лежит `.env.example`, сгенерированный из реестра `core.config.env_spec`
- плейсхолдеры `dev-only-*` из `.env.example` работают локально, а в production их
  отвергают на старте и ядро (`validate_env`), и бот (`bot/src/config.ts`)
- `JWT_SECRET` не короче 32 символов, `BOT_WEBHOOK_SECRET` не короче 16
- ключи GigaChat и DaData остаются в ядре, браузеру не отдаются
- pre-commit ловит приватные ключи (`detect-private-key`)
- пароль Redis в консоли `./maxapp redis` передаётся через окружение, а не
  аргументом: аргументы видны в `ps`

## Gateway

| Что              | Настройка                                                                                                                                         |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| TLS              | только TLS 1.2 и 1.3, сертификат Let's Encrypt, http отдаёт 301 на https                                                                          |
| заголовки        | HSTS на год с поддоменами, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `Permissions-Policy` (камера и микрофон только самому мини-аппу) |
| CSP              | `default-src 'self'`, скрипты только свои и мост `st.max.ru`, `object-src 'none'`, `frame-ancestors` только MAX                                   |
| частота запросов | API 50 в секунду с IP, вход 2 в секунду, тяжёлые ручки (помощник, сборка, загрузки) 2 в секунду; сверх лимита 429                                 |
| размер тела      | вход 64 КБ, API 5 МБ, ручки с файлами 11 МБ, вебхук 1 МБ                                                                                          |
| соединения       | не больше 10 на вход и 50 на API с одного IP                                                                                                      |
| лишние пути      | `.env`, `.yaml`, `.sql`, `.bak`, `.php`, скрытые файлы отвечают 404; `server_tokens off`                                                          |
| вебхук бота      | наружу открыт только путь `BOT_WEBHOOK_PATH`, SDK сверяет `x-max-bot-api-secret` с `BOT_WEBHOOK_SECRET`                                           |

Настройки лежат в `gateway/templates/default.conf.template` и
`gateway/snippets/security_headers.conf`, лимиты и CSP держит замок
`core/tests/repo/test_infra_config.py`

## Контейнеры

- наружу открыт только gateway (80 и 443), PostgreSQL и Redis доступны лишь во
  внутренней сети compose, у Redis обязательный пароль
- `api`, `bot` и `certbot`: read-only файловая система, `tmpfs` для `/tmp`,
  `cap_drop: ALL`, `no-new-privileges`, лимиты памяти и числа процессов
- `db`, `redis`, `gateway`: `cap_drop: ALL` и точечные `cap_add` под свои
  entrypoint'ы, `no-new-privileges`
- процессы ядра и бота работают не от root (`USER app`, `USER node`)
- базовые образы с явными версиями, зависимости ставятся строго по lock-файлам,
  контекст сборки ядра не видит другие сервисы

## Персональные данные

| Данные                 | Где и сколько                                                                                               |
| ---------------------- | ----------------------------------------------------------------------------------------------------------- |
| профиль MAX            | id, имя, username, аватар из initData; в PostgreSQL                                                         |
| реквизиты и документы  | в PostgreSQL у владельца-пользователя, файлы DOCX и PDF на диске в томе `app_data`                          |
| фото, сканы, голосовые | не сохраняются: обрабатываются в памяти, у значения хранится только строка-источник и уверенность           |
| файлы у GigaChat       | загружаются на один запрос и удаляются сразу после ответа                                                   |
| логи                   | без секретов, initData и значений полей документов                                                          |
| журнал документа       | факты (создан, собран, отправлен, отклонено поле) без персональных данных                                   |
| бэкапы                 | суточный `pg_dump` и снимок перед выкаткой, файлы `0600` (`umask 077`)                                      |
| удаление               | документ, организация, клиент удаляются пользователем; учётка проверяющих с её данными удаляется `--revoke` |

## Зависимости

- версии закреплены lock-файлами: `core/uv.lock` (Python, uv) и `pnpm-lock.yaml`
  (Node), сборка образов идёт с `--frozen`
- `./maxapp audit` запускает `pnpm audit` и `pip-audit` по `core/uv.lock`. Последний
  прогон: уязвимостей не найдено
- транзитивные зависимости инструментов с исправленными уязвимостями подняты через
  `overrides` в `pnpm-workspace.yaml`
- pnpm придерживает только что опубликованные версии (минимальный возраст релиза),
  исключения перечислены в `pnpm-workspace.yaml`
- скрипты установки пакетов запрещены всем, кроме `esbuild` (`allowBuilds`)
- прямые зависимости, которые импортирует код, объявлены явно в `core/pyproject.toml`
  и `package.json` сервисов

## Известные ограничения

- готовые файлы лежат на диске контейнера без шифрования на уровне приложения,
  объектного хранилища и чистки сирот нет
- refresh-cookie в dev идёт по http с `SameSite=Lax` и без `Secure`: dev-стенд не
  для настоящих данных
- лимиты частоты считаются по IP на одном gateway, общего лимита на кластер нет
- аудит зависимостей запускается вручную, в `./maxapp check` его нет: базы
  уязвимостей требуют сети
